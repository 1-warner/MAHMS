# MAHMS API

REST API for MAHMS, the Mobile Appointment and Healthcare Management System of Mpilo Central
Hospital. Built by team doodoobops for XISD6329 Task 2.

Node.js 20 with Express, data in PostgreSQL. Firebase Authentication stays the identity
provider: the Android app and the website sign the user in, then send the Firebase ID token
with every request. The API verifies that token and maps the e-mail onto a row in `users`,
which is where the hospital role lives. The API never receives or stores a password.

## What is in here

```
backend/
  db/mahms_schema.sql   tables, keys, constraints and the receipt-number sequence
  db/mahms_seed.sql     demo data, at least ten rows per table, matching the app's seeder
  src/server.js         entry point, reads .env, listens
  src/app.js            builds the Express app (kept separate so the tests can mount it)
  src/db.js             PostgreSQL pool, query helpers, transactions
  src/auth.js           Firebase token verification, users lookup, role checks
  src/refs.js           accepts either a server UUID or the app's local row id
  src/routes/           one file per area: me, appointments, doctors, prescriptions,
                        payments, emergencies
  test/api.test.js      40 route tests (node:test + supertest) against a real database
  openapi.yaml          full API description, 13 paths
```

## Endpoints

| Method | Path | Who | What |
|---|---|---|---|
| GET | `/health` | anyone | Service and database health. No token needed. |
| GET | `/api/me` | signed in | The account, its role, and its linked patient or doctor record. |
| POST | `/api/patients/me` | Patient | Create or update the caller's own patient record. |
| GET | `/api/doctors?department=` | signed in | List doctors, optionally by department. |
| GET | `/api/departments` | signed in | List departments. |
| GET | `/api/appointments?patientId=&doctorId=&date=&status=` | signed in | List appointments. |
| POST | `/api/appointments` | signed in | Book an appointment. |
| PATCH | `/api/appointments/:id` | signed in | Change one. A patient may only cancel. |
| GET | `/api/prescriptions?patientId=&dispensed=` | signed in | List prescriptions. |
| POST | `/api/prescriptions` | Doctor | Write a prescription. |
| PATCH | `/api/prescriptions/:id` | Pharmacist, Doctor, Admin | Mark it dispensed. |
| GET | `/api/payments?patientId=&status=` | signed in | List payments. |
| POST | `/api/payments` | signed in | Record a payment, which issues the receipt. |
| GET | `/api/receipts/:paymentId` | signed in | The receipt for one payment. |
| GET | `/api/emergencies?status=active` | signed in | List SOS alerts. |
| POST | `/api/emergencies` | signed in | Raise an SOS alert. |
| PATCH | `/api/emergencies/:id` | Responder, Nurse, Doctor, Admin | Change its status. |

The full description, with every field and every error, is in `openapi.yaml`. Paste that file
into <https://editor.swagger.io> to read it as a page, or import it into Postman
(Import > File > openapi.yaml) to get a ready-made collection.

## Two ids for the same record

Server ids are UUIDs, generated by the database. The Android app keeps its own Room row ids,
which are plain numbers. So every table the app writes to also has a `client_ref` column: the
app sends its local id there and the server stores it as a unique key.

That gives two useful things:

- The app can find "its" server row again without keeping a second set of ids.
- Posting the same `clientRef` twice updates the first row instead of creating a second one,
  so the app can retry safely after a dropped connection.

Any endpoint that takes an id accepts either form. `GET /api/appointments?patientId=1` and
`GET /api/appointments?patientId=5f2c...` both work.

## Who can see what

- A **Patient** only ever reads and writes their own appointments, prescriptions, payments,
  receipts and alerts. The `patientId` in a query is ignored for a patient account, so asking
  for someone else's data returns your own, not theirs.
- A patient may **cancel** their own appointment but not confirm or complete it.
- Only a **Doctor** may write a prescription, and the prescribing doctor is taken from the
  signed-in account rather than the request body.
- Only a **Pharmacist**, Doctor or Admin may mark a prescription dispensed.
- Only a **Responder**, Nurse, Doctor or Admin may change the status of an SOS alert.
- A brand new e-mail always becomes a **Patient**. A caller cannot choose its own role by
  signing up, which closes the hole the Firestore-only build had.

## Run it locally

You need Node.js 20 or newer and a PostgreSQL database. The quickest database is Docker:

```bash
docker run -d --name mahms-pg \
  -e POSTGRES_USER=mahms -e POSTGRES_PASSWORD=mahms -e POSTGRES_DB=mahms \
  -p 5432:5432 postgres:16-alpine
```

Then:

```bash
cd backend
npm install
cp .env.example .env     # then edit DATABASE_URL if yours differs
npm run db:reset         # loads the schema, then the seed data
npm start
```

`npm run db:reset` needs the `psql` client on your PATH. Without it, load the two files any
way you like, for example:

```bash
docker exec -i mahms-pg psql -U mahms -d mahms < db/mahms_schema.sql
docker exec -i mahms-pg psql -U mahms -d mahms < db/mahms_seed.sql
```

Check it is up:

```bash
curl http://localhost:3000/health
```

### Verifying real tokens

`/health` works straight away, but `/api/...` needs to verify the Firebase ID token, which
needs a service account from the team's Firebase project:

1. Firebase console > Project settings > Service accounts > Generate new private key.
2. Save the JSON into `backend/` (it is git-ignored) and point `GOOGLE_APPLICATION_CREDENTIALS`
   at it in `.env`, or paste the same JSON into `FIREBASE_SERVICE_ACCOUNT` on one line.

Without either, `/api/...` answers `503` with a message saying verification is not configured.
That is deliberate: the server refuses rather than letting unverified requests through.

To call the API by hand, get a token from a signed-in app with
`FirebaseAuth.getInstance().currentUser?.getIdToken(false)` (it is also written to Logcat
under the `MAHMS` tag) and send it as a bearer token:

```bash
curl -H "Authorization: Bearer <idToken>" http://localhost:3000/api/me
```

## Tests

```bash
cd backend
DATABASE_URL=postgres://mahms:mahms@localhost:5432/mahms npm test
```

40 tests covering health, authentication, role checks, patient scoping, booking, retry
behaviour, prescriptions, payments, receipt numbering and the SOS flow.

They run against a **real** PostgreSQL database rather than a mock, because the routes are
mostly SQL and a mock would not prove the constraints work. The suite reloads
`mahms_schema.sql` and `mahms_seed.sql` before it starts, which **drops every table first**,
so always point `DATABASE_URL` at a throw-away database, never at the deployed one.

So the tests do not need a Firebase service account, they set `MAHMS_AUTH_MODE=test`, which
makes the API accept a stub token of the form `Bearer test:<email>` instead of a real one.
**Never set `MAHMS_AUTH_MODE` on a deployed server.** It is refused when `NODE_ENV=production`,
and the server prints a warning on start-up when it is on.

The GitHub Actions workflow runs the same tests against a PostgreSQL service container on
every push, alongside the Android unit tests.

## Deploying

Any host with Node.js and a managed PostgreSQL works. Render, Railway and Fly.io all have a
free tier, and a Supabase database can host the same schema.

1. Create a PostgreSQL instance and copy its connection string.
2. Create a web service from this repository with root directory `backend`,
   build command `npm install`, start command `npm start`.
3. Set the environment variables: `DATABASE_URL`, `PGSSL=require` (managed databases usually
   insist on TLS), and `FIREBASE_SERVICE_ACCOUNT` with the service-account JSON.
   Do **not** set `MAHMS_AUTH_MODE`.
4. Load the schema and the seed into the new database once.
5. Open `/health` to confirm it answers, then put that base URL into the Android app's
   `MAHMS_API_BASE_URL` (see the main README) and into this file at the top.

Set `ALLOWED_ORIGIN` to the website's origin once the site is deployed. It defaults to `*`,
which is fine for the demo but too open for anything real.

## Known limitations

- The payment gateway is simulated. The payment record, the receipt and the revenue figures
  are real, but no money moves. A live gateway such as Paynow would replace that one step.
- There is no refresh or pagination beyond a 500-row cap per list request. The demo data is
  far smaller than that.
- Role changes are done directly in the database. There is no admin endpoint for promoting an
  account yet, which is the next thing worth adding.
- The API trusts the clock of the host for `raised_at` and `created_at`.
